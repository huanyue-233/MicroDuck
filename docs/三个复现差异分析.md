# 三个 MicroDuck 复现项目差异分析

> **分析日期：2026-09-25**  
> 本文分析的三个仓库来自当前目录的 `Related Repo.md`：
>
> 1. [LuwuDynamics/xgoduck_hardware](https://github.com/LuwuDynamics/xgoduck_hardware)
> 2. [fanhao375/microduck-replica](https://github.com/fanhao375/microduck-replica)
> 3. [JoyandAI/OpenMicroDuck](https://github.com/JoyandAI/OpenMicroDuck)
>
> **说明：** 当前 `list.md` 是 BOM 清单，并没有仓库地址；因此本文将 `Related Repo.md` 中的三个项目作为分析对象。

---

## 1. 总体结论

这三个项目并不是三套完全相同的 MicroDuck 复刻方案，而是三种不同的工程路线：

| 项目 | 核心定位 | 更适合的目标 |
|---|---|---|
| **xgoduck_hardware** | 基于 Arduino Uno Q 重新设计控制器、扩展板和机器人硬件 | 快速做出一套独立的鸭形双足机器人硬件 |
| **microduck-replica** | 对官方 MicroDuck 的机械、软件和电控接口进行逆向复刻 | 最大程度理解和复现原始 MicroDuck |
| **OpenMicroDuck** | 将 MicroDuck 做成更开放、可扩展、可长期维护的社区平台 | 建立自己的开源硬件、软件和 RL 复现生态 |

一句话概括：

> **xgoduck_hardware 是“重新做一套硬件”，microduck-replica 是“尽量还原官方 MicroDuck”，OpenMicroDuck 是“把 MicroDuck 改造成更开放的社区平台”。**

> **共同点：三条路线中所有带 “1910” 的舵机名称（`Feetech 1910`、`HD-1910`、`HD-1910-C001`）都指向同一颗舵机——飞特（Feetech）HD-1910 系列智能舵机。** 走 1910 路线时执行器本体相同，差异集中在主控平台、总线适配、机械结构和训练方案。

## 2. 三个项目的基本差异

### 2.1 xgoduck_hardware

XGO Duck hardware 项目主要提供：

- 机器人结构 STL；
- Arduino Uno Q 相关硬件；
- 自有扩展板原理图和 PCB；
- SMT BOM；
- Pick-and-place 文件；
- 装配指南；
- 电池、舵机、线束和打印件说明。

它的重点是把机器人硬件重新组织成一套可以独立生产和组装的方案，而不是兼容官方 MicroDuck 的软件栈。

其运行时、固件和 Web UI 位于独立的 runtime 仓库中。因此 `xgoduck_hardware` 本身更接近“硬件发布包”，不能单独代表完整的软件复现方案。

### 2.2 microduck-replica

`microduck-replica` 的重点是逆向官方 MicroDuck：

- 从官方 MJCF 和 STL 反推关节结构；
- 研究官方软件中的控制接口；
- 提供 XL330 和 HD-1910 两条舵机路线；
- 维护中文 BOM、装配、线束和调试记录；
- 提供 Feetech 舵机适配思路；
- 配合 Radxa Zero 3W、官方 RPI Robot HAT 和社区 `imu_to_dxl`；
- 记录零位、ID、串口、总线和策略适配问题。

它不是单纯的“重新设计一个外形相似的机器人”，而是尝试回答：

> 官方 MicroDuck 的机械、控制、仿真和部署接口如何还原成社区可以重复构建的实体？

### 2.3 OpenMicroDuck

OpenMicroDuck 的定位更偏平台化和开源化：

- 使用 HD-1910 等国产智能舵机；
- 维护自己的结构和 BOM；
- 设计 Zero HAT 与 IMU 转接方案；
- 提供桌面调试到整机集成的分阶段流程；
- 维护 HD-1910 相关的 RL fork 和参数；
- 强调软件、硬件、BOM、训练环境和文档的开放性；
- 方便后续社区继续扩展和衍生。

它不只想“复刻一台机器”，还想形成一个可以被别人继续修改的 MicroDuck 衍生平台。

## 3. 主控平台差异

| 维度 | xgoduck_hardware | microduck-replica | OpenMicroDuck |
|---|---|---|---|
| 主控方向 | Arduino Uno Q | Radxa Zero 3W / 官方运行时方向 | Radxa Zero 3W |
| 控制器特点 | Linux + MCU 双处理器平台 | 更接近官方 RK3566 软件组织 | 复用 Radxa，同时维护开放扩展板 |
| 官方 `robotd` 兼容性 | 不应假定兼容 | 目标是尽量兼容或适配 | 部分复用官方思路并进行衍生适配 |
| 软件工作量 | 需要使用 XGO runtime | 主要是官方 runtime 与 Feetech 适配 | 需要维护平台化 runtime 与 RL 适配 |
| 适合目标 | 独立硬件产品 | 官方行为复现 | 长期开放平台 |

### 3.1 xgoduck：Uno Q 路线

Arduino Uno Q 让 xgoduck 可以将 Linux 侧和 MCU 侧职责分开：

- Linux 侧适合运行高层应用、Web UI 和模型；
- MCU 侧适合执行低层实时控制；
- 自有扩展板负责舵机、IMU、电源和接口。

优点是系统可以完全独立于 Radxa 和官方 HAT；缺点是官方 MicroDuck 的软件、串口映射、daemon 和策略部署方式不能直接照搬。

### 3.2 microduck-replica：官方软件兼容方向

该项目围绕 Radxa Zero 3W 和官方 MicroDuck 软件架构进行适配，目标是保留：

```text
robotd / 50 Hz 控制环
        ↓
RobotIo 接口
        ↓
Feetech 舵机适配层
        ↓
HD-1910 总线
```

这是三者中最接近官方 MicroDuck 运行时的路线。

### 3.3 OpenMicroDuck：Radxa 平台化路线

OpenMicroDuck 也使用 Radxa Zero 3W，但更重视：

- 自有 HAT；
- IMU 转接板；
- 桌面调试阶段；
- 社区可复用的接线、BOM 和训练环境。

它不完全等同于官方 MicroDuck，而是将 Radxa 作为一个开放平台基础。

## 4. 舵机与执行器差异

> **重要前提：三个仓库中所有带 “1910” 的舵机名称——`Feetech 1910`、`HD-1910`、`HD-1910-C001`——指向同一颗舵机：飞特（Feetech）HD-1910 系列智能舵机。它们不是三种不同的舵机，只是各项目对同一型号的不同写法。** 当三个项目都选择 1910 路线时，执行器本体完全相同；真正的差异在主控平台、总线适配、机械结构和训练方案。

### 4.1 舵机型号

| 项目 | 主要舵机路线 | 实际舵机型号 | 主要影响 |
|---|---|---|---|
| xgoduck_hardware | Feetech 1910 ×15 | 飞特 HD-1910 | 配合 Uno Q 和 XGO runtime |
| microduck-replica | XL330 或 HD-1910 | 飞特 HD-1910（低成本路线） | 可研究官方等价路线，也可降低成本 |
| OpenMicroDuck | HD-1910-C001 ×15 | 飞特 HD-1910-C001 | 面向国产舵机的独立训练和部署 |

> 三个项目对同一颗舵机有三种写法：`Feetech 1910`、`HD-1910`、`HD-1910-C001`，实际都是飞特 HD-1910。只要走 1910 路线，舵机硬件通用，差异全部来自舵机之外的系统集成。

### 4.2 XL330 与 HD-1910 不能直接互换

这里的对比是 **Dynamixel XL330** 与 **飞特 HD-1910** 两种不同家族的舵机；三个仓库中出现的各种 “1910” 名称都指后者（飞特 HD-1910），并不存在“几种不同的 1910”。

即使两者都能完成类似的关节运动，也不能只把一颗舵机拆下来换成另一颗。至少需要重新确认：

- 舵机外形和输出轴高度；
- 舵盘孔位和安装方式；
- 总线协议；
- 寄存器地址；
- 位置单位和角度方向；
- 速度和力矩表示方式；
- PID 或增益设置；
- 位置回差；
- 通信延迟；
- 电压范围；
- 温度和过载行为；
- 机械质量、惯量和质心。

因此：

> **“15 个舵机”是数量相同，不代表三套方案的电气、机械和策略接口相同。**

### 4.3 三个项目的取舍

三个项目中的 1910 都是同一颗飞特 HD-1910，取舍差异只在于“把它接入哪套平台”：

- **xgoduck_hardware：** 重点是让 Feetech 1910 和 Uno Q 硬件配套工作。
- **microduck-replica：** 同时保留 XL330 和 HD-1910，强调两条路线之间的差异。
- **OpenMicroDuck：** 直接把 HD-1910 作为开放复现的主要对象，并围绕它维护参数和训练环境。

> 三者都选 1910 时舵机完全相同，选择差异只在于：是否同时保留 XL330 路线、用哪套主控与 HAT 驱动、围绕 HD-1910 维护多少训练资料。

## 5. PCB、HAT 和 IMU 方案差异

### 5.1 xgoduck_hardware：一体化 Uno Q 扩展板

XGO 路线使用自己的扩展板，主要负责：

- Uno Q 安装和扩展；
- 舵机通信；
- 半双工串口；
- QMI8658A 六轴 IMU；
- 电源分配；
- 舵机接口；
- 电池接口；
- 相关外围器件。

这是一套围绕 Uno Q 设计的硬件系统，不能直接替代 RPI Robot HAT。

### 5.2 microduck-replica：官方 HAT + 社区 `imu_to_dxl`

该路线使用：

```text
Radxa Zero 3W
        +
官方 RPI Robot HAT
        +
社区重建的 imu_to_dxl
        +
HD-1910 或 XL330 总线
```

其优势是与官方 MicroDuck 的软件组织和接口更接近；其不足是部分 IMU 转接板和装配细节属于社区逆向，不是官方完整生产资料。

### 5.3 OpenMicroDuck：Zero HAT + IMU 转接板

OpenMicroDuck 更强调分阶段集成：

#### 桌面调试阶段

- 主控和舵机驱动板放在机器人外部；
- 使用外部电源；
- 逐颗设置舵机 ID；
- 连接显示器或调试终端；
- 先完成单舵机和全总线测试。

#### 整机集成阶段

- 安装 Zero HAT；
- 安装 IMU 转接板；
- 检查线束和电源；
- 再将已经通过验证的控制软件放入机身。

这条流程特别适合第一次复现，因为能把“硬件故障”和“整机装配问题”分开定位。

## 6. 机械结构差异

### xgoduck_hardware

特点：

- 提供结构 STL；
- 配套 Assembly Guide；
- 结构和扩展板一起设计；
- 更像一套可以直接按其 BOM 组装的硬件包。

它的机械零件不应默认与官方 MicroDuck 或其他两个仓库逐件互换。

### microduck-replica

特点：

- 通过 MJCF 和 STL 反推原始结构；
- 对关节树、零件关系、装配位置进行逆向；
- 维护 XL330 和 HD-1910 不同版本；
- 对舵盘凸起、孔位、轴承座和配合件进行修改；
- 更强调“还原官方结构关系”。

对于 HD-1910 路线，不能直接打印官方 XL330 结构后期待无修改装配完成。

### OpenMicroDuck

特点：

- 更强调结构开放和后续衍生；
- 对国产舵机安装和打印配合进行优化；
- 配合 Zero HAT 和 IMU 方案；
- 结构、BOM、软件和训练环境组合得更完整。

它不一定与 `microduck-replica-cad` 的每一个零件一一兼容，但更适合作为一个独立版本长期维护。

## 7. 软件与控制架构差异

### 7.1 xgoduck_hardware：独立 runtime

软件关系大致是：

```text
Arduino Uno Q
        ↓
XGO 自有固件 / runtime / Web UI
        ↓
Feetech 1910 舵机
```

硬件仓库本身并不等于完整的软件系统。想复现完整功能，需要同时研究它对应的 runtime 仓库。

### 7.2 microduck-replica：接近官方 daemon 架构

软件路线大致是：

```text
官方或社区 robotd
        ↓
RobotIo / FeetechIo
        ↓
HD-1910 舵机总线
```

重点工作包括：

- Feetech 协议适配；
- 舵机状态读取；
- ID 和零位配置；
- 串口占用排查；
- IMU 同步读取；
- 50 Hz 控制环；
- ONNX 策略加载；
- 安全限位和异常回退。

### 7.3 OpenMicroDuck：硬件、软件和训练一起开放

OpenMicroDuck 试图把以下内容放在同一套社区工程中：

- 结构和 BOM；
- HAT 和 IMU；
- runtime；
- 舵机适配；
- RL fork；
- HD-1910 参数；
- sim2real 文档。

它更适合希望继续开发自己的衍生版本，而不是只完成一次装配的团队。

## 8. 强化学习和 sim2real 差异

| 维度 | xgoduck_hardware | microduck-replica | OpenMicroDuck |
|---|---|---|---|
| RL 重点 | 依赖 XGO runtime 和策略 | 在官方 RL 接口基础上适配 | 维护 HD-1910 方向的 RL fork |
| 执行器建模 | 依赖配套 runtime | 参考或引入 BAM 参数 | 直接面向 HD-1910 参数 |
| 官方 ONNX 复用 | 不应假定 | XL330 更有希望；HD-1910 需适配 | 不应直接当作即插即用 |
| 训练目标 | 让 Uno Q 方案工作 | 尽量复现官方 MicroDuck | 建立国产舵机开放基线 |
| sim2real 重点 | 平台独立性 | 还原官方接口和行为 | 公开参数、流程和衍生能力 |

### 8.1 Observation 和 Action

MicroDuck 常见的策略接口为：

```text
61 维 Observation → 策略网络 → 14 维 Action
```

含义是：

- **Observation：** 策略看到的传感器和状态数据；
- **Action：** 策略输出的关节控制量。

这两个数字不是简单的硬件规格，而是软件接口契约。只要观测顺序、单位、坐标系或动作缩放不一致，策略就可能无法工作。

### 8.2 三个项目的训练差异

- **xgoduck_hardware：** 不能只看硬件仓库判断其 RL 训练流程，还需要配套 runtime 仓库。
- **microduck-replica：** 更关注官方接口与国产舵机适配，HD-1910 需要重新校准和训练。
- **OpenMicroDuck：** 更直接地把 HD-1910 参数和训练环境作为平台的一部分公开。

## 9. 开源程度与资料类型差异

| 资料类型 | xgoduck_hardware | microduck-replica | OpenMicroDuck |
|---|---|---|---|
| 打印 STL | 有 | 有/来自逆向和改件 | 有/持续维护 |
| 可编辑 CAD | 有限或依版本 | 有，配套 CAD 仓库 | 有，面向开放衍生 |
| PCB 原理图 | 有 | 官方 HAT + 社区转接 | 有自有 HAT/IMU 方向 |
| BOM | 有 | 社区逆向 BOM | 有平台化 BOM |
| 装配指南 | 有 | 有，且包含踩坑记录 | 有分阶段流程 |
| 运行时 | 独立仓库 | 接近官方 runtime | 社区平台化 runtime |
| RL 训练资料 | 依赖配套仓库 | 中高 | 高 |
| 逆向分析 | 较少 | 很深入 | 中等 |
| 社区扩展性 | 中高 | 中高 | 很高 |

### 许可证注意

代码、PCB、CAD、STL、策略和文档可能使用不同许可证。不能因为代码使用 Apache-2.0，就默认所有模型和图纸也可以自由商用。发布自己的复现版本前，应逐项检查：

- 软件许可证；
- 机械模型许可证；
- PCB 和硬件许可证；
- 策略模型许可证；
- 商标和项目名称使用限制。

## 10. 与当前 `list.md` BOM 的匹配关系

当前 `list.md` 更接近 **microduck-replica + OpenMicroDuck 的 HD-1910/Radxa 路线**，不是 xgoduck_hardware 的完整 BOM。

| `list.md` 项目 | xgoduck_hardware | microduck-replica | OpenMicroDuck |
|---|---|---|---|
| HD-1910-C001 ×15 | 舵机方向相近，但控制器不同 | 直接匹配 | 直接匹配 |
| Radxa Zero 3W | 不匹配，XGO 主要使用 Uno Q | 匹配 | 匹配 |
| RPI Robot HAT | 不匹配，XGO 使用自有扩展板 | 匹配 | 部分匹配/对应 Zero HAT 路线 |
| `imu_to_dxl` | 不属于 XGO 主路线 | 直接对应 | 对应 IMU 转接思路 |
| NP-F550 | 不对应 XGO README 的核心配置 | 社区复刻中常见 | 需与具体 OpenMicroDuck 版本核对 |
| FE-URT-2 / URT2 | 不一定是 XGO 必需工具 | 重要调试工具 | 有帮助但不是唯一方案 |
| `-FT` 飞特版图纸 | 不保证兼容 | 直接对应 | 结构思路相近但不能默认互换 |

因此，`list.md` 不应被理解为三个仓库通用的统一采购清单，而应标注为：

```text
HD-1910 + Radxa Zero 3W + HAT/IMU 转接板的社区复现 BOM
```

## 11. 三套方案的工程选择建议

### 11.1 想尽快做出独立实体

选择：

```text
xgoduck_hardware
+ 对应 xgoduck runtime
+ Arduino Uno Q
+ XGO 自有扩展板
+ Feetech 1910
```

适合：

- 接受不兼容官方 Radxa 软件；
- 重点是先做出可以运行的硬件；
- 希望获得一套比较集中的 PCB、BOM 和装配资料。

### 11.2 想尽量复现官方 MicroDuck

选择：

```text
microduck-replica
+ XL330 或 HD-1910 二选一
+ Radxa Zero 3W
+ 官方 RPI Robot HAT
+ imu_to_dxl
+ 官方 runtime / 社区适配
```

如果优先官方行为一致性，选择 XL330；如果优先采购成本，选择 HD-1910，但必须接受协议适配、结构改件、重新标定和重新训练。

### 11.3 想建立长期开放平台

选择：

```text
OpenMicroDuck
+ HD-1910
+ Radxa Zero 3W
+ Zero HAT
+ IMU 转接板
+ OpenMicroDuck RL fork
```

适合：

- 打算长期维护 CAD、PCB、BOM 和训练参数；
- 希望加入新的舵机、主控和传感器；
- 希望将复现过程公开给其他人重复；
- 重视开源许可证和社区协作。

## 12. 最终推荐

结合当前 `list.md` 的物料配置，建议不要直接采用 xgoduck_hardware 的 Uno Q 路线，而采用以下组合：

```text
microduck-replica 的逆向分析和软件适配资料
        +
OpenMicroDuck 的平台化 BOM 与桌面调试流程
        +
HD-1910-C001 ×15
        +
Radxa Zero 3W 2 GB
        +
对应的 HAT / IMU 转接方案
        +
HD-1910 专用仿真和策略训练
```

但机械和电气版本必须固定，不能随意混用：

```text
机械基线：microduck-replica-cad 或 OpenMicroDuck 二选一
舵机基线：HD-1910-C001 ×15
主控基线：Radxa Zero 3W 2 GB
电气基线：一套确定的 HAT + IMU 转接方案
软件基线：一个固定的 runtime 分支
训练基线：一个固定的 HD-1910 RL fork
```

### 最终排序

如果按当前“做出实体并继续研究”的目标排序：

1. **microduck-replica：最适合作为工程复现主线**
2. **OpenMicroDuck：最适合作为开放平台和长期维护主线**
3. **xgoduck_hardware：最适合作为独立 Arduino Uno Q 硬件路线**

> **microduck-replica 解决“如何还原 MicroDuck”；OpenMicroDuck 解决“如何把它做成开放平台”；xgoduck_hardware 解决“如何脱离官方 Radxa 栈，重新做一套可运行的鸭形机器人硬件”。**
